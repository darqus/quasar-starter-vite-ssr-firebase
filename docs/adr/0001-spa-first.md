# ADR 0001: SPA-first deployment

Статус: **принято**
Дата: 2026-11-03

## Контекст

Проект назывался `quasar-starter-vite-ssr-firebase`, но фактически собирался и
деплоился как SPA:

- `firebase.json` публикует `dist/spa`;
- в `quasar.config.ts` нет режима `ssr`;
- серверного entry и `ssrContext` нет;
- Firebase Client SDK и `LocalStorage` используются без серверных guard-ов.

В коде оставались ветки `QUASAR_SERVER` и комментарии про SSR, что создавало
ложное впечатление о поддерживаемой серверной рендеринге.

## Решение

Проект — **SPA-first**. Мы не поддерживаем SSR до появления отдельной задачи с
требованиями к серверной сессии, SEO и инфраструктуре.

Практические следствия:

1. Убраны SSR-ветки из `src/router/index.ts` и комментарии в `src/stores/index.ts`.
2. Роутер использует `createWebHistory` или `createWebHashHistory` по
   `VITE_ROUTER_MODE`.
3. Название пакета/репозитория не переименовывается в рамках этого ADR, но
   README и документация не должны обещать SSR.
4. Если SSR понадобится, это будет отдельный проект: серверный entry, Firebase
   Admin/Session Cookies, отказ от `LocalStorage` на сервере, per-request Pinia,
   гидрация. Оценка и дизайн — отдельным ADR.

## Последствия

- Меньше сложности и нет мёртвых веток.
- Нельзя использовать `window`/`document`/`LocalStorage` в коде, который
  когда-либо задумывался как универсальный, — это осознанно.
- Будущий SSR потребует явной миграции, а не «включения флага».
